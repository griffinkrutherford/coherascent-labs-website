The Focus with Tock carousel keeps its normal behavior. Twelve manual revolutions of the long hand complete one revolution of the short hand and reveal the **Easter Egg set**. Either direction works for this first secret. Advancing the clock seven days, or fourteen clockwise revolutions of the short hand (168 long-hand revolutions), reveals the **Golden Egg set**. The first revolution counts toward the fourteen; unlocking the first reward does not stop tracking. Reversing cancels net travel, so seven days backward do not earn the Golden Egg. Both reveals persist until the page is reloaded.

Each set contains an item for every app wardrobe category. The reveal requests its current timer combination from `GET /v1/public/tock-wardrobe-code?set=standard|golden&sequenceVersion=2` on the production API. Both sets require three ordered steps: select the first time, genuinely move the risk slider to any different position, then select a distinct final time. No exact risk percentage is required. Timer values remain five-minute wheel values from 5 through 120. Keep the timer open while entering the numbered steps; if the first time is already selected, change it away and back before continuing. The existing app slider requires a positive Moon Rock balance to move; zero-balance users cannot currently complete that step. Entering the sequence starts no session and spends nothing. The app verifies the current code and persists ownership through its authenticated wardrobe redemption endpoint. These are freely shareable cosmetic secrets, not proof of website interaction or eligibility for paid benefits.

The v2 response retains the first time in `durationMinutes`, zero legacy `riskLevel`, and server timestamps. It adds `sequenceVersion:2`, `riskRule:"any-adjustment"` and exactly three ordered entries: `{control:"time",value:first}`, `{control:"risk",value:0}`, `{control:"time",value:final}`. The risk entry's zero is a wire marker, never a 0% target or a requirement to return to zero. The website renders it only as an instruction to move the slider. Genuine movement is tracked by the compatible mobile client; the public issuer response alone cannot prove a physical gesture. The API's default/unrecognized-version behavior remains v1, including the existing two-step standard and three-step golden contracts, for older clients. The website's parser retains a separate strict v1 path, while this page explicitly requests and requires v2.

The additive server bridge preserves the original v1 exact patterns first, then accepts a complete new three-step sequence from compatible older v1 clients. The frozen installed-client core can emit only integer middle-risk values from 0 through 5. It does not support unrestricted high-risk or fractional movement, and small changes within a quantized setting may not count. The new v2 client records genuine raw adjustments with finite values from 0 through 10. This is an app-build boundary; there is no OTA, and a website push does not update installed phones. The website therefore tells visitors to update for unrestricted movement without advertising an exact risk-percentage target.

Codes change at ten-minute UTC boundaries. The card shows the server’s remaining lifetime using monotonic elapsed time, conservatively subtracting request latency. It hides the old combination before refreshing, including after connection errors, and offers a retry button. Request and refresh timers stop while the page is hidden; returning to the page fetches fresh codes for any revealed sets. No fixed pair is embedded in the markup as a fallback. V2 responses must match the requested set/version, exact three-step order, any-adjustment rule, zero risk marker, first-time metadata, distinct final time, valid wheel range and a positive server lifetime of at most ten minutes. Legacy or malformed responses remain unavailable rather than displaying a percentage target or fallback. Server enforcement is authoritative, including at expiry.

Only explicit clock-pointer movement and arrow-key turns earn progress. Autoplay, carousel tabs, side-phone clicks, Home/End keys, snapping, initial pointer grabs, center-pin jumps and other pointers do not. A cancelled or lost pointer cannot keep contributing travel. The reveal uses a polite live region without moving focus during dragging; its changing countdown has live announcements disabled. Mobile touch input, reduced-motion preferences and keyboard access retain the existing carousel behavior.

The website note explicitly requires the app update for unrestricted slider movement. Deploy and read-verify the additive v2 API before publishing the updated website, then distribute the compatible app build. Older installed builds keep their existing redemption contracts and the bounded bridge described above. Closing the app timer, starting a session or switching accounts clears partial input; the compatible app coalesces wheel/slider movement and keeps rapid alternation in order.
